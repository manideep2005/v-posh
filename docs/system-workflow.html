1 · Rate Limiting & Cooling Periods

All authentication-sensitive endpoints are protected by a fixed-window rate limiter (server/middleware/rateLimit.js). Every auth route uses the shared authLimiter; there is no per-user lockout — limiting is keyed per IP address + endpoint.

10max attempts / window

per IP, per endpoint bucket. The 11th request in the window is blocked.

15 minfixed window

Counter resets exactly 15 minutes after the window opened — not rolling.

429HTTP response when blocked

With a Retry-After header telling the client the exact seconds remaining.

1 MBJSON body limit

Global express.json cap; uploads go through multer (10 MB files, 5 attachments).

How the limiter works internally

  1. Key = <client IP>:<route path bucket> — the same IP hitting different endpoints has separate counters.
  2. First request in a window opens a counter starting at 1; each further request increments it.
  3. When count > 10, the request is rejected with 429 and a Retry-After header (exact remaining seconds).
  4. The window self-clears: a background sweep deletes entries older than 15 minutes, and any entry whose windowStart has expired is transparently restarted on the next hit.
// server/routes/auth.js — one shared limiter for ALL auth routes
const authLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 10 });

// server/middleware/rateLimit.js — rejection behaviour
res.setHeader('Retry-After', String(retryAfterSec));
res.status(429).json({
  success: false,
  message: 'Too many attempts. Please wait a few minutes before trying again.'
});
⚠️ "Too many attempts" — what the user experiences After the 10th failed/any attempt from one IP on one endpoint within 15 minutes, every further call — even correct credentials — returns 429 Too Many Attempts. The cooling period is the remainder of the fixed window: worst case ~15 minutes, best case a few seconds (if the window is about to reset). The exact time is always sent in the Retry-After response header.

ℹ️ Fixed window vs rolling window This is a fixed-window limiter: the counter opens on the first request and dies exactly 15 minutes later regardless of activity. A burst of 10 requests at minute 14:59 still blocks request #11 at 15:00+ε only until the new window opens. Memory is bounded by a periodic sweep that deletes expired entries.
🚫 Client-side polling does NOT bypass the limiter Push polling runs every 2s and QR polling every 3s from the browser — all of these hit /push/poll or /qr/poll and consume the same 10-per-15-min budget. A 90-second push wait consumes ~45 poll calls. In practice a single user can exhaust the poll bucket in one or two login waits. Recommended fix: raise the limit or exempt the poll routes with a separate, higher rateLimit bucket.

3 · KratosID Push & QR Pipeline (detailed)

3.1 — Push login (two-step, Vercel-safe)

Designed for serverless: no request lives longer than a few seconds. Pending requests are persisted in MongoDB (pending_pushes collection), not in server memory, so they survive cold starts and work across Vercel lambda instances.

1

POST/api/auth/kratosid/push/start limiter 10/15m

Body: { email }. Server validates the email, rejects disabled accounts, then calls KratosID /add_request to fire the mobile push. Extracts a 36-char push token.

404 if email not registered on KratosID · 403 if no product access / account disabled · 200 { success, token }

Persists { id: token, email, createdAt } in pending_pushes and lazily deletes stale entries older than 3 minutes.

2

POST/api/auth/kratosid/push/poll limiter 10/15m

Body: { token }. Client calls this every 2 seconds, up to 45 attempts (~90 s).

Server: loads pending entry → rejects 404 if missing or older than 120 s (server-side cooling/expiry) → asks KratosID /get_data for status:

  • pending… → 200 { approved: false, status: 'pending' } — keep polling
  • expired / Authorization denied → entry deleted, denied
  • Authorization timeout → entry deleted, timeout
  • Approval payload (JSON array / Verification) → approved → entry deleted → JWT issued
3

JWT issuance & auto-provision

If no DB user exists for the approved email, one is created with the role derived from the email domain (see §2). Both paths return { success, token, user }. Audit log written (USER_LOGIN_KRATOSID or STUDENT/FACULTY_REGISTERED_KRATOSID).

⏱️ Push timing summary Client polls every 2 s, gives up after 45 attempts = 90 s ("Push timed out."). Server-side pending entry expires after 120 s. KratosID's own request window is ~2 minutes. Effectively the user has ~90 seconds to tap Approve on the phone.

3.2 — QR login

1

POST/api/auth/kratosid/qr/start

No body needed. Server calls KratosID startQrLogin() which registers a login session and returns the QR payload. Client renders it as a QR code and shows a countdown.

200 { success, token, qrData… }

2

POST/api/auth/kratosid/qr/poll

Body: { token }. Client polls every 3 seconds, ≤45 attempts (~90 s plus countdown grace).

Server long-polls KratosID waitForQrLogin(token, { timeout: 85000 }) — i.e. a single poll call can block up to 85 s waiting for the scan. On approval, the raw payload is parsed for the user's email; missing email → 400.

  • Denied by user → 401 "QR login denied by user."
  • Timed out / expired → 401 "QR login timed out or expired."
  • Approved + email → find-or-create user → 200 { token, user }
🔄 Why QR works better on Vercel QR uses KratosID's own server-side session state (token lives at KratosID), whereas push originally used an in-memory Map that broke on serverless. Push is now DB-backed too, so both work on Vercel.

3.3 — Legacy single-call verify

POST /api/auth/kratosid/verify sends the push and long-polls for approval inside one request (≤55 s). Kept for compatibility but the two-step push flow is preferred because Vercel serverless functions time out before 55 s on some plans.

4 · Google SSO Pipeline

1

Client obtains Google credential

Either a Google ID token (Google Identity Services / google-one-tap) or an access token (useGoogleLogin() implicit flow). Sent to:

POST/api/auth/google { idToken } —or— POST/api/auth/google-access { accessToken }

2

Server-side verification

  • ID-token path: google-auth-library verifyIdToken() checks signature, expiry and audience (GOOGLE_CLIENT_ID).
  • Access-token path: server calls googleapis.com/oauth2/v3/userinfo with the bearer token and reads the profile.

Invalid/expired token → 401.

3

Domain gate

Email domain must be @vitapstudent.ac.in or @vitap.ac.in, unless the address is in WHITELIST_EMAILS. Otherwise → 403 "Only @vitapstudent.ac.in … allowed."

4

Find-or-create user → JWT

Existing disabled account → 403. New email → auto-provision with domain-derived role, student/employee ID parsed from the local-part (e.g. mani.23bce0042@… → ID 23BCE0042). Google fields (googleId, avatar, authProvider) patched onto existing users. Returns 200 { token, user }.

⚠️ Known production gotcha: origin_mismatch Google rejects sign-in unless the exact browser origin is registered in Google Cloud Console → Credentials → OAuth client → Authorized JavaScript origins. Add both http://localhost:5173 and the production Vercel URL.

5 · Password Login, Signup & Recovery

5.1 — Signup POST/api/auth/student/signup

  • Required: name, email, password (≥8 chars), studentId, department. Optional: year, phone.
  • Uniqueness checks on both email and student ID → 409 on duplicates.
  • Password hashed with bcrypt (10 rounds) → user created with role student → JWT returned immediately (auto-login).

5.2 — Login POST/api/auth/login

Body: { email, password, expectedRole? }. Checks in order:

  1. Missing fields → 400
  2. Unknown email → 401 generic "Invalid credentials" (no user enumeration)
  3. status === 'disabled' → 403 "account has been deactivated"
  4. bcrypt compare fails → 401 same generic message
  5. Role mismatch vs expectedRole → 403, with one exception: admin portal also accepts super_admin and faculty accounts
  6. Success → lastActiveAt updated, audit log, 200 { token, user }

5.3 — Recovery: forgot / reset

  • POST/forgot-password — always returns the same generic message (account existence never disclosed). Internally generates a 32-byte random token, stores only its SHA-256 hash with a 30-minute expiry, and emails the single-use link through the password_reset service. When no SMTP credentials are configured the link is returned as devLink instead, which the portal only renders in that local-development case.
  • POST/reset-password — validates the token hash + expiry, sets the new bcrypt password, and immediately nulls the token so it is single-use.
  • Password change (/change-password) requires a valid JWT and the current password, and triggers the security_alert email so any credential change is reported to the account holder.

6 · Complaint Lifecycle Workflow

Every route below requires the Authorization: Bearer <jwt> header. Roles: student, faculty, admin, super_admin.

1

Submission — student or faculty

POST/api/student/complaints / /api/faculty/complaints — creates the complaint, generates a case reference, sets SLA clock, optional attachments via POST/api/uploads (multipart, ≤5 files, 10 MB each, stored in GridFS).

2

Admin triage & allocation

GET/api/admin/complaints — queue with filters · POST/api/admin/complaints/:id/allocate — assign an officer · /bulk-allocate · /auto-allocate (workload-based routing via GET/api/admin/workload).

3

Resolution loop

PUT/api/admin/complaints/:id/status — transitions (in-review → investigating → resolved etc.), each transition is audit-logged · POST/api/admin/complaints/:id/updates — case notes / progress posts.

4

Student controls

PUT/POST/api/student/complaints/:id/pause — pause with reason + email confirmation (POST alias added for Vercel edge-body robustness) · DELETE/POST/api/student/complaints/:id/delete — withdraw the complaint (POST alias for the same reason).

5

SLA monitoring & escalation

GET/api/student/complaints-sla — per-complaint SLA countdown data rendered by the client SLACountdown component. Overdue cases escalate through the admin panel; super admin monitors via /api/super-admin/workload.

7 · PDF Document Generation

Server-side rendering with pdfkit (server/services/pdf.js). Documents include a 4-page status report: complaint summary, status history, POSH Act guidelines, and rights/remedies. Every document embeds a verification QR / doc ID so it can be validated publicly.

EndpointRoleOutput

GET /api/pdf/student/complaints/:id/status-reportstudent4-page status report + guidelines
GET /api/pdf/admin/complaints/:id/acknowledgementadmin / super_adminAdmin copy of acknowledgement
GET /api/pdf/admin/complaints/:id/status-reportadmin / super_adminAdmin copy of status report
GET /api/pdf/verify/:docIdpublicDocument authenticity verification
GET /api/pdf/case/:refIdpublicPublic case lookup by reference ID

Responses carry Content-Type: application/pdf, an RFC 5987 Content-Disposition attachment filename, and Content-Length (needed for reliable binary downloads through the Vercel edge). The frontend fetches the file as a blob, triggers a.click(), and revokes the object URL after a 1-second delay to avoid the race that cancelled downloads.
